# 2.4 — Middleware chung: xử lý lỗi, logging, audit log

Jira: APDDMP-16. Yêu cầu liên quan: NFR-07 (Logging và Audit) trong SRS (APDDMP-4), mục "Cross-cutting" trong kiến trúc (APDDMP-7), route `GET /audit-events` trong thiết kế API (APDDMP-9).

## Tổng quan

Ba phần chạy cho mọi request, độc lập với nghiệp vụ, nối với nhau bằng một **traceId**:

| Phần | Làm gì | Ở đâu |
|---|---|---|
| Xử lý lỗi | Mọi lỗi trả cùng một dạng JSON, không lộ chi tiết nội bộ | `api/error/GlobalExceptionHandler`, `api/error/ProblemJson`, `application/common/ErrorCode` |
| Logging | Mỗi request một dòng log; mọi dòng log có `[traceId]`; ghi ra file xoay vòng | `api/filter/RequestLoggingFilter`, `application.yml` (`logging.*`) |
| Audit log | Lưu bền ai làm gì, lúc nào, từ IP nào; admin tra cứu được | `application/admin/AuditService`, bảng `audit_logs`, `GET /v1/audit-events`, trang web `/admin/audit-log` |

```
request ─▶ RequestLoggingFilter: sinh traceId, đặt vào MDC, trả header X-Trace-Id
             │
             ├─▶ Spring Security ── lỗi 401/403 ─▶ ProblemJson (traceId)
             ├─▶ Controller ─▶ Service ── ghi audit_logs (traceId, IP)
             │                    └── lỗi ─▶ GlobalExceptionHandler (traceId)
             └─▶ log: "[traceId] METHOD /path -> status (ms)"
```

Từ `traceId` mà người dùng báo lại (có trong JSON lỗi và header `X-Trace-Id`), nhóm tìm được toàn bộ dòng log và các dòng audit của đúng request đó.

## 1. Xử lý lỗi

- Dạng chuẩn RFC 7807, `Content-Type: application/problem+json`:
  ```json
  { "type": "about:blank", "title": "...", "status": 409, "detail": "...",
    "code": "EMAIL_ALREADY_EXISTS", "message": "Email đã được đăng ký",
    "traceId": "35c6f7d1-..." }
  ```
  Lỗi validation có thêm `errors: [{ field, message }]`. Trường `message` giữ lại để web cũ (`apiClient.ts`) đọc được.
- Lỗi nghiệp vụ: service ném `ApiException(ErrorCode.X)`. Danh sách mã và HTTP status nằm trong `ErrorCode`.
- 401/403 phát sinh ở tầng Spring Security (trước controller) được `ProblemJson` trả cùng định dạng.
- Lỗi database mà service chưa tự bắt:
  - trùng unique / vi phạm ràng buộc → `409 DATA_CONFLICT`
  - xung đột phiên bản (optimistic lock) → `412 VERSION_CONFLICT`
  - deadlock / hết thời gian chờ khóa → `409 DATA_CONFLICT`

  Câu SQL không bao giờ được trả ra ngoài, chỉ ghi log `WARN`.
- Lỗi không lường trước → `500 INTERNAL_ERROR` với thông báo chung. Stacktrace chỉ nằm trong log, kèm `traceId`.

## 2. Logging

- `RequestLoggingFilter` chạy đầu tiên trong chuỗi filter. Nó luôn tự sinh `traceId` mới và không tin header từ client.
- `logging.pattern.correlation` in `[traceId]` vào **mọi** dòng log của request, không riêng dòng của filter.
- Ghi ra console và file `logs/smartdrone-backend.log`; đổi đường dẫn bằng biến môi trường `LOG_FILE`. File xoay vòng theo ngày hoặc khi quá 10MB, giữ 14 ngày, tổng tối đa 1GB. Thư mục `logs/` nằm trong `.gitignore`.

Ví dụ:
```
2026-11-22T22:18:03.438+07:00 INFO ... [35c6f7d1-4c9e-...] c.s.api.filter.RequestLoggingFilter : GET /api/v1/addresses -> 401 (66 ms)
```

## 3. Audit log

### Dữ liệu

Dùng chung bảng `audit_logs` với phần quản trị FR-02. Bảng chỉ thêm mới, không sửa, không xóa.

| Cột | Ý nghĩa |
|---|---|
| `action` | mã thao tác, vd `LOGIN_FAILED` |
| `actor_id`, `actor_email`, `actor_role` | người thực hiện; rỗng nếu không xác định (vd đăng nhập bằng email không tồn tại) |
| `target_type`, `target_id` | đối tượng bị tác động |
| `detail` | mô tả ngắn, tối đa 1000 ký tự; **không bao giờ** chứa mật khẩu, token, secret |
| `ip_address` | IP kết nối trực tiếp (không tin `X-Forwarded-For`) |
| `trace_id` | traceId của request |
| `occurred_at` | thời điểm |

### Thao tác được ghi

| Nhóm | action |
|---|---|
| Xác thực | `USER_REGISTERED`, `LOGIN_SUCCEEDED`, `LOGIN_FAILED`, `LOGOUT`, `REFRESH_TOKEN_REUSED` |
| Tài khoản | `PASSWORD_CHANGED`, `USER_ACCESS_CHANGED`, `ACCOUNT_CREATED`, `ACCOUNT_UPDATED`, `ACCOUNT_LOCKED`, `ACCOUNT_UNLOCKED` |
| Quản trị | `ROLE_PERMISSIONS_UPDATED`, `SETTINGS_UPDATED` |
| Trạm | `STATION_CREATED`, `STATION_UPDATED`, `STATION_STATUS_CHANGED` |
| API key | `API_KEY_ISSUED`, `API_KEY_REVOKED`, `API_KEY_ROTATED` |

Đổi trạng thái đơn hàng **không** ghi vào audit vì `order_status_history` đã lưu đầy đủ người làm, lý do và traceId.

### Cách ghi (cho người thêm nghiệp vụ mới)

`AuditService` có ba hàm:

- `record(actorId, action, targetType, targetId, detail)`: ghi **cùng transaction** với thao tác. Nếu thao tác rollback thì dòng audit cũng mất, nên log không bao giờ ghi một việc đã không xảy ra.
- `recordForCurrentUser(action, targetType, targetId, detail)`: như trên, người làm lấy từ tài khoản đang đăng nhập.
- `recordIndependently(...)`: transaction riêng (`REQUIRES_NEW`), dùng cho lần thử thất bại mà ngay sau đó ném lỗi (vd đăng nhập sai). Lỗi khi ghi audit chỉ được log, không làm hỏng request.

### Tra cứu

- API: `GET /api/v1/audit-events`, chỉ đọc, cho `SYSTEM_ADMIN` và `LOGISTICS_MANAGER` (APDDMP-3). Lọc theo `action`, `actorId`, `targetType`, `targetId`, khoảng `[from, to)`; phân trang, mới nhất trước. Chi tiết: [audit-api.md](../05-api/audit-api.md).
- Web: menu **Audit Log** (`/admin/audit-log`). Trang có bộ lọc thao tác, đối tượng và khoảng ngày; bấm vào người thực hiện để chỉ xem thao tác của người đó; thao tác cần chú ý (đăng nhập sai, token bị dùng lại, khóa tài khoản) được tô màu.

## Triển khai

- H2 / `ddl-auto=update` tự tạo bảng và cột.
- Database SQL Server dùng chung: chạy một lần `backend/scripts/2.4-audit-logs.sql` (thêm cột `ip_address`, `trace_id` và các index; chạy lại nhiều lần vẫn an toàn).

## Giới hạn hiện tại

- Chưa có chính sách xóa audit log cũ; bảng tăng dần theo thời gian.
- Job chạy nền (gửi thông báo, dọn file) và WebSocket chưa có `traceId` riêng; log của chúng hiện `[]`.
- Dòng log request chưa ghi `userId` của người gọi.
- IP lấy từ kết nối trực tiếp. Nếu sau này đặt sau reverse proxy thì cần cấu hình proxy tin cậy để lấy IP thật.
