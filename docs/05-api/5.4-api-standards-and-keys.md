Mục tiêu và phạm vi

Chuẩn hóa REST API hiện có: tài liệu OpenAPI đầy đủ hơn (mô tả, lỗi, xác thực, versioning), và thêm cơ chế API key cho hệ thống ngoài gọi vào một tập endpoint giới hạn, tách hẳn khỏi luồng JWT của web và mobile. Không đổi route hay hành vi của bất kỳ API đã có trước đó.

Versioning

Version nằm trong đường dẫn: /v1/.... Quy ước giữ nguyên như đang dùng trong toàn bộ repository, chỉ nói rõ thành chính sách: thay đổi không phá vỡ hợp đồng (thêm trường mới, thêm endpoint mới) vẫn ở /v1. Thay đổi phá vỡ hợp đồng (đổi kiểu một trường, đổi ý nghĩa trường, xóa trường, đổi route) phải lên /v2; /v1 tiếp tục chạy song song cho tới khi mọi phía (web, mobile, hệ thống ngoài đang cầm API key) đã chuyển xong. Không có task nào trong giai đoạn 4-6 bị bắt đổi route theo task này.

Swagger

Mở http://localhost:5000/api/swagger-ui.html, chọn nhóm ở góc trên bên phải:

business-v1: toàn bộ API cho web/mobile, xác thực Bearer JWT.
admin-v1: API quản trị (hiện chỉ có quản lý API key), vẫn JWT nhưng chỉ SYSTEM_ADMIN.
integration-v1: API cho hệ thống ngoài, xác thực bằng API key, không liên quan JWT.

Mỗi task 4-6 khi thêm endpoint mới chỉ cần gắn đúng @Tag/@Operation/@SecurityRequirement như các controller hiện có, Swagger tự nhận và xếp đúng nhóm, không cần sửa OpenApiConfig.

Error envelope

Mọi lỗi, ở mọi nhóm API, trả cùng một khuôn dạng JSON đã có từ trước (không đổi): type, title, status, detail, code, message, traceId. code là mã ổn định để lập trình xử lý theo (ví dụ API_KEY_UNAUTHORIZED), message/detail chỉ để hiển thị và có thể đổi câu chữ. traceId dùng để tra log khi cần.

API key cho hệ thống ngoài
Kiến trúc

API key và JWT là hai cơ chế xác thực tách biệt hoàn toàn, chạy trên hai filter chain riêng của Spring Security:

Mọi route hiện có (/v1/orders, /v1/stations...) tiếp tục đi qua chain JWT như cũ, không đổi gì.
Route mới /v1/integration/\*\* chỉ chấp nhận API key qua header X-Api-Key, không bao giờ chấp nhận Bearer JWT.

Nhờ tách chain, một API key không thể gọi được bất kỳ route nghiệp vụ nào (/v1/orders, /v1/stations...), và JWT của người dùng không gọi được route /v1/integration/\*\*. Đây là yêu cầu bắt buộc của task: không dùng API key để bỏ qua JWT hay giả làm người dùng.

Định dạng key

X-Api-Key: {id}.{secret}, trong đó id là UUID của key (để tra nhanh, không phải dò toàn bộ bảng), secret là 32 byte ngẫu nhiên mã hóa base64url. Cơ sở dữ liệu chỉ lưu SHA-256 của secret; secret gốc chỉ xuất hiện đúng một lần trong response của lúc cấp hoặc xoay vòng, không đọc lại được sau đó.

Scope

Mỗi key được cấp một hoặc nhiều scope trong IntegrationScope (ORDERS_READ, STATIONS_READ), mỗi scope khớp đúng một endpoint dưới /v1/integration/. Key chỉ gọi được route khớp scope đã cấp; gọi route khác (kể cả route hợp lệ nhưng không thuộc scope) bị từ chối 403, không phải 404, để không gợi ý route đó có tồn tại hay không.

Endpoint quản trị (chỉ SYSTEM_ADMIN, qua JWT như các route admin khác)

POST /api/v1/admin/api-keys — cấp key mới. Body: clientName, scopes (mảng), expiresAt (tùy chọn, null = không hết hạn), rateLimitPerMinute (tùy chọn, mặc định lấy từ cấu hình hệ thống). Trả 201 kèm secret — đây là lần duy nhất secret xuất hiện.

GET /api/v1/admin/api-keys?page=1&pageSize=20 — danh sách key, không bao giờ có secret hay hash của nó. Mỗi phần tử có effectiveStatus tính sẵn (ACTIVE/EXPIRED/REVOKED) để không phải tự so ngày.

POST /api/v1/admin/api-keys/{id}/revoke — thu hồi ngay, trả 204. Mọi request sau đó bằng key này bị từ chối ngay lập tức, không có độ trễ cache.

POST /api/v1/admin/api-keys/{id}/rotate — đổi secret, giữ nguyên scope và id, trả 200 kèm secret mới. Secret cũ ngưng hoạt động ngay khi rotate xong.

Endpoint cho hệ thống ngoài

GET /api/v1/integration/stations (cần scope STATIONS_READ) — danh sách trạm: id, tên, tọa độ, trạng thái.

GET /api/v1/integration/orders/{id}/status (cần scope ORDERS_READ) — trạng thái đơn tối thiểu: orderId, status, statusLabel, terminal, updatedAt. Cố ý không có tên/điện thoại/địa chỉ người nhận hay bất kỳ thông tin cá nhân nào, theo đúng nguyên tắc đã áp dụng ở các API khác của hệ thống (ví dụ thông báo trạng thái task 4.9).

Giới hạn tần suất

Mỗi key có rateLimitPerMinute riêng (mặc định lấy từ app.api-keys.default-rate-limit-per-minute, hiện là 60). Vượt giới hạn trả 429 kèm code: API_KEY_RATE_LIMITED. Bộ đếm là cửa sổ trượt 60 giây, giữ trong bộ nhớ của instance đang xử lý request — đúng với một instance; chạy nhiều instance cần chuyển sang bộ đếm tập trung (ví dụ Redis), chưa làm ở task này.

Vòng đời và audit

Trạng thái admin đặt trực tiếp chỉ có ACTIVE/REVOKED; hết hạn (expiresAt) được tính ngay lúc xác thực mỗi request, không có job nền để tự chuyển trạng thái. Mỗi lần cấp/thu hồi/xoay vòng được ghi một dòng log có cấu trúc (API_KEY_ISSUED, API_KEY_REVOKED, API_KEY_ROTATED) kèm ai thực hiện và thời điểm. Đây chưa phải audit trail đầy đủ như route /v1/audit-events (route đó cho toàn hệ thống, SYSTEM_ADMIN, chưa có controller/service triển khai — nằm ngoài phạm vi task 5.4), chỉ đủ để tra log khi cần điều tra một API key cụ thể.

Vì sao không ảnh hưởng mobile

Mobile (Flutter) tiếp tục dùng JWT y như web, không bắt buộc và không nên dùng API key thay JWT. API key chỉ dành cho hệ thống bên ngoài tổ chức (đối tác tích hợp), không phải client chính thức của sản phẩm.

Giới hạn và việc còn lại
Bộ đếm tần suất trong bộ nhớ, chỉ đúng với một instance backend.
Chưa có audit trail đầy đủ cho mọi thao tác hệ thống (route /v1/audit-events vẫn chưa có controller, không thuộc phạm vi 5.4).
Mới có 2 endpoint tích hợp mẫu (stations, orders/.../status). Thêm endpoint mới: thêm rule vào IntegrationPolicy, thêm giá trị vào IntegrationScope, thêm phương thức vào IntegrationController/IntegrationQueryService.
Chưa có giao diện web cho admin quản lý API key (hiện chỉ có API); nếu cần, có thể làm một trang riêng dùng đúng 4 endpoint /v1/admin/api-keys ở trên.
Chưa chạy được build/test trong môi trường của tôi (không tải được Maven Central), cần xác nhận ở máy bạn.
